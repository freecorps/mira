# Fork maintenance and release baseline

This fork keeps its Orange Pi deployment changes while regularly importing
`miracodeai/mira`. Upstream synchronization is an explicit merge so published
history is never rewritten and local changes remain auditable.

## Supported baseline

- Runtime: Linux with Python 3.11 or 3.12.
- Container platforms: `linux/amd64` and `linux/arm64`.
- State: SQLite by default; PostgreSQL remains optional.
- Deployment tag: `ghcr.io/freecorps/mira:edge` after every green `main` push.
- Local development: Python 3.12 from `.python-version`.

Python versions outside the CI matrix are unsupported, even if dependency
resolution happens to succeed. Add a version to CI before widening the
`requires-python` range.

## Synchronizing upstream

Use a dedicated branch and a merge commit:

```bash
git remote get-url upstream
git fetch --all --prune
git switch main
git pull --ff-only origin main
git switch -c chore/sync-upstream-YYYY-MM-DD
git merge --no-ff upstream/main
```

Resolve conflicts by preserving upstream behavior first, then reapplying only
the fork contracts that remain necessary. In particular, confirm these
invariants after every sync:

- CI and release workflows still target `linux/amd64,linux/arm64`.
- `deploy/orangepi/` still points at the fork's `edge` image.
- updater health checks and rollback remain enabled.
- local verdict behavior remains covered by its tests.

Keep the sync merge separate from any product feature. Small follow-up commits
for CI/compatibility are acceptable; review features belong in their own PR.

## Required validation

Run locally:

```bash
uv sync --locked --extra dev --extra serve --extra bedrock
uv run pre-commit run --all-files
uv run pytest tests/ --ignore=tests/evals --ignore=tests/test_integration.py
cd ui/mira && npm ci && npm run build
```

The PR CI then provides the Linux and container checks that a Windows machine
cannot reproduce faithfully:

1. Python 3.11 and 3.12 suites.
2. Native `amd64` image build and CLI/UI smoke tests.
3. QEMU `arm64` execution, `/health`, existing SQLite compatibility, and
   previous-image compatibility.
4. Orange Pi updater failure-and-restore with real ARM64 images, plus its
   focused shell contract test.

Do not merge while any blocking job is red. The project-wide `mypy` job is
advisory until its synchronized-upstream backlog is retired; new code should
still be typed and must not add avoidable errors.

## Image publication and verification

Only a push to `main` publishes `edge`, and publication depends on every
blocking CI job. Release tags additionally depend on the eval workflow.

Both edge and release images carry:

- an OCI SBOM generated by BuildKit;
- max-level BuildKit provenance;
- a signed GitHub artifact attestation pushed alongside the image in GHCR.

Verify provenance after publication:

```bash
gh attestation verify \
  oci://ghcr.io/freecorps/mira:edge \
  --repo freecorps/mira
```

## Schema and rollback policy

SQLite migrations must remain additive or otherwise readable by the previous
image for at least one release. A schema-changing PR must extend the ARM smoke
test or add a focused migration fixture that proves:

1. existing rows survive opening with the candidate;
2. the candidate serves `/health` using that database;
3. the previous image can reopen the candidate-touched database; or
4. when backward compatibility is impossible, the deployment procedure takes
   and restores an explicit database backup before rolling the image back.

The Orange Pi updater intentionally exits non-zero after a successful rollback
so systemd and logs retain evidence that the attempted deployment failed.
